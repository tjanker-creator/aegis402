The model can be fooled.
The money can't move.

AEGIS402 puts the spending policy inside the Algorand payment group itself. A compromised agent can decide to overspend — the transfer still cannot come into existence.

The problem

An agent's reasoning layer is also its authorization layer

Give an agent a wallet and the thing that decides is the thing that signs. Every spending limit that lives in the agent's own process lives inside the blast radius: whoever controls the agent controls the limit.

The obvious fix — a smarter model — does not hold. We tested it. Frontier models refused our injection outright:

“I won't comply with that ‘priority override’ — it's an embedded instruction in page content attempting to redirect funds to an unverified address.”

Good. And irrelevant, because the attack that works needs no jailbreak at all.

What actually breaks

A poisoned supplier beats a perfect model

In x402 the receiving address is declared by the server in its 402 response. An agent has no independent ground truth about who it is paying. So we showed a real Claude agent an ordinary, professional supplier page with an attacker's address on it. No manipulation, no override language.

agent  “Payment for one real-time market data query from MarketFeed API”
to EQFRW7U57YY5N5ZMVN45PYFE6OPG7SATWZEJ5DCZO2WQLBGRSS7KIBGU6Y · 0.02 USDC

The model did nothing wrong. It was asked to buy data, it bought data, it paid the published address. There is no unethical instruction to refuse. The data was poisoned, not the intent — and alignment has nothing to object to.

The mechanism

One atomic group, one fate

A guard application call rides in the same Algorand group as the USDC transfer. If the guard rejects, simulate fails, the facilitator never submits, and the payment does not exist. The facilitator is unmodified, and because its fee transaction pools the fee for the whole group, the guard costs the paying agent nothing.

[0]fee-payerunsigned → facilitator signs at settle
[1]guard app-callimmutable policy: cap + receiver allowlist
[2]payment axfersigned by the vault, not by the agent

The obvious question is whether the agent can just leave the guard out. It cannot. The account is rekeyed to a LogicSig that signs a transfer only when a call to that guard, naming that transaction's index, is present. Omitting it fails. Substituting a friendlier guard fails. The agent's operational key signs the guard call and holds no money at all.

Honesty

What we do not protect against

The harness is built to print red rows, and the repository ships a file listing its own bypasses. The important ones:

  • The ledger gates the payment, not the action. An agent that abandons the protocol can still do unpaid damage. We never claim “no verification → no action” as a ledger property.
  • Two of the seven refusals are the facilitator's, not ours. We inherit them and say so.
  • We are not claiming the primitive. Guarding a transfer with a grouped app call is long-standing Algorand practice, the x402 AVM scheme explicitly permits extra transactions, and prior work — KirkeLabs' oaa-agent-kit, agent-budget, Akita's ARC-58 plugins — enforces the same intent by other means. Ours travels inside the payment group, on an ordinary account holding ordinary USDC, against an unmodified facilitator.
  • Not audited. TestNet only.

What's next

Guards, not a product

The guard slot is an interface, not a feature. A payment group holds up to sixteen transactions and the facilitator pays for them, so a payment can carry several independent guards from different authors — a spending cap, a velocity limit, a terms commitment, an audit receipt — all settling or failing together.

Next: publish the guard interface as an ARC so guards compose across wallets and clients; a public vault on MainNet holding real USDC that anyone is invited to drain; and hardening for other agents' wallets rather than only our own.

One open question for the facilitator's operators is in SPEC-NOTE.md: the fee pool covers guard transactions the facilitator never asked for. We think that subsidy is a feature — it makes security free for the payer — but it should be a deliberate one.
